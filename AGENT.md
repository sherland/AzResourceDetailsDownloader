# AGENT.md

Operating notes for agents (and humans) working in this repo — things that aren't obvious from reading the code, or that cost real time to figure out. See [README.md](README.md) for full feature documentation, the catalog format, and known limitations.

## Authentication — read this before debugging a failed `--run`

This tool depends on **two independent auth surfaces**, and confusing them wastes time:

1. **Azure CLI / ARM session** (`az login`) — used for all resource provisioning and management-plane calls.
2. **Portal browser session** (`.auth/storage_state.json`, gitignored) — a saved Playwright browser session used only for portal screenshot capture (`--login` mode).

Either can expire without the other doing so. Key lessons:

- **`AADSTS70043` during a `--run`**: this tenant enforces a conditional-access sign-in-frequency policy, so the CLI session expires periodically no matter how recently you authenticated some other way. Fix: run `./authenticate.ps1`.
- **`az account show` succeeding is *not* proof the session is valid.** It can succeed even when the actual token scope this tool needs (`https://management.azure.com/.default`) has already expired. Verify with:
  ```
  az account get-access-token --resource https://management.azure.com --query expiresOn -o tsv
  ```
  Trust this over `az account show`.
- **A plain `az login` can silently no-op.** If there's an existing SSO session, `az login` alone can reuse it without resetting the conditional-access clock, so the CLI session keeps expiring on the same schedule. Use `./authenticate.ps1` instead of a bare `az login` — it runs `az logout` first to force a genuinely fresh login, then `az login`, then this tool's own `--login` mode to refresh the portal session too.
- Run `./authenticate.ps1` proactively before starting a long unattended batch (`--run` without `--only`), not just reactively after a failure — a mid-batch expiry wastes every unit that runs after it.

## Windows-specific: `.gitignore` matches case-insensitively

Found live: `.gitignore` had `output/` (no leading slash), meant to ignore the *generated* `output/` artifacts folder at the repo root. On Windows, git's ignore matching is case-insensitive, so that pattern also silently matched `src/AzResourceDetailsDownloader/Output/` — the C# namespace folder holding `CategoryResolver.cs`, `OutputWriter.cs`, `CategoryKey.cs`, `ArmTypeKey.cs`, `OutputNormalizer.cs`. Those files were **never tracked by git**, across the project's entire history — `git status` and `git add -A` gave no hint anything was missing, since git silently ignores what `.gitignore` tells it to.

Fixed by anchoring the pattern to the repo root (`/output/` instead of `output/`). If you add another top-level ignore whose name could collide with a source folder elsewhere in the tree (case-insensitively), anchor it the same way. After touching `.gitignore`, sanity-check:
```
git check-ignore -v <path>     # should print nothing for files you expect to be tracked
git ls-files -- <folder>       # should list the source files you expect
```

## Category resolution for `output/{category}/{armType}/`

Categorization is layered across two config files — for an unmatched armType, add config, don't edit `CategoryResolver.cs`:
1. `config/resource-abbreviations.json` — auto-generated by `fetch-resource-abbreviations.ps1` from Microsoft's official abbreviations table. Fully overwritten every time that script runs — never hand-edit it.
2. `config/category-overrides.json` — hand-curated, never touched by any script. Add an entry here for any armType Microsoft's table doesn't cover, even via `CategoryResolver`'s parent-type walk.

Anything unmatched by both lands in `output/uncategorized/` — worth checking after adding new catalog entries.

## Long-running `--run` batches can show no console output for a while — that's normal

Portal screenshot capture is serialized behind one shared browser session, and several catalog entries take 10-45+ minutes to provision (see README's "Slow-provisioning entries"). Before assuming a background run has hung, check for real progress rather than just watching the log:
```
find output -maxdepth 3 -newermt "10 minutes ago"
```
and confirm the `dotnet`/`AzResourceDetailsDownloader.exe`/Playwright/`chrome-headless-shell` processes are still alive.
